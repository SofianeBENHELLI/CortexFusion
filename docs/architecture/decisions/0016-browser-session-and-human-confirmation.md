## Context

Implementation follow-up, 6 October02:54 UTC: the proxy inventory is now29 method/route pairs after three native personal import/collection GETs. The console reads receipts, collection names and full sources with current native permissions and bounded responses; it does not create/process/retry/cancel imports or sign/publish decisions. A synthetic native HTTP acceptance passes five grouped checks without changing publication or ACLs; four new Chrome scenarios remain untested. This additive read path does not weaken or complete the independent human-decision boundary below.

The console currently asks for a tenant and bearer token, retains them in memory and loses its session on refresh. This development path cannot be the normal collaborator/owner experience. `ApiConnection` already clears API caches on logout and checks domain membership through `/me`; those boundaries must survive the new login flow.

Identity and decisions are separate capabilities. Native `auth.rs` verifies issuer, audience, signature and expiry, parses the explicit tenant header, then domain authorization checks persisted membership. It does not derive that header from an ID token. The gateway profile will derive it from the verified API token's tenant claim. `confirmation.rs` requires an independent trusted-host signature for an exact canonical command, with the same actor/tenant, action, command hash, a short validity interval and a single-use identifier. A session alone must not turn an agent-prepared proposal into a human-approved publication.

The checked-in configuration names only an example identity provider. No production issuer, client registration, hosting origin or trusted human-confirmation product has been verified. This decision does not create any external account or authorize deployment.

## Decision

### Login boundary

Introduce a small same-origin browser session gateway (BFF), independent of the knowledge service. Use OIDC Authorization Code flow with server-side token exchange, PKCE S256, per-attempt state and nonce, exact registered callback and issuer, and validated token claims. Code flow exchanges the authorization code at the token endpoint; current OAuth security guidance recommends PKCE for confidential clients as well. [OIDC Core §3.1](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowAuth), [OAuth Security BCP §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1).

The choices below are Cortex design constraints; the implementation status above distinguishes the completed boundary from remaining delivery:

- Browser stores an opaque session cookie, not API/refresh tokens, signing keys or a tenant selected without verification. Production cookies are HttpOnly, Secure, host-only, SameSite=Lax and Path=/; Lax permits the configured top-level authorization callback. Enforce Origin and a per-session CSRF token on mutations. Logout is a protected POST. Do not rely on SameSite alone.
- Gateway holds tokens server-side. Validate ID token for login; use an access token with the Cortex API audience for API calls. Never substitute an ID token, infer an owner role from frontend state or mint an unrestricted service token. Resolve the tenant only from verified identity/mapping; the core still verifies the access token, tenant consistency and current membership.
- Proxy only the configured Cortex API origin and an explicit operation/method allowlist. Strip browser-supplied Authorization, tenant, cookie and hop-by-hop headers before constructing upstream requests. Apply existing response budgets, request/time limits and cancellation. Do not create an arbitrary URL proxy or relay a human confirmation on ordinary read requests.
- Keep session and authorization-attempt stores bounded by count and expiry. An initial single-process local implementation may revoke all sessions on restart; that behavior must be explicit. Multi-instance rollout requires shared expiry/revocation and refresh coordination, with tokens protected at rest. No silent per-process sessions in a multi-instance deployment.
- Bound session lifetime by configured idle/absolute limits and verified upstream token validity. Refresh, when the provider permits it, is serialized per session and adopts rotated credentials atomically. An ambiguous refresh failure requires login again; it must not replay a mutation or guess that a token remains valid.
- Restore only an allowlisted relative app route after login. Persist opaque navigation identifiers and supported view parameters, not questions, source text or credentials. Reject absolute/scheme-relative return URLs. Re-read `/me` and domain membership before any selected conversation/source is loaded. Expiry/logout clears cached private data; permission errors never restore stale content as a fallback.
- Preserve manual bearer entry behind an explicit local development configuration until the new path passes acceptance. No automatic owner login, production demo identity, long-lived localStorage credential or fabricated SSO success.

### Human decision boundary

Keep the existing independent confirmation verifier and canonical command digest. A gateway login authenticates the user; it does not sign approval receipts. The confirmation signer remains outside the knowledge API, model/runtime and browser, with a separately operated trust boundary.

The owner flow must show the exact action, domain, proposal revision, digest, reason and publication effect. A trusted interactive host authenticates the human and confirms that precise command, returning the existing short-lived, one-use receipt. Core rechecks actor, current permissions, revision and digest at execution. A changed proposal or expired/replayed receipt requires a new review. Do not place the private key in Vite, a frontend asset or a generic BFF auto-sign endpoint. Keep preparation, human decision and publication as distinct steps with their own idempotency/recovery contracts.

The available MCP/trusted-host path remains usable while the product confirmation adapter is implemented. AUD-05 stays open until the console can complete the governed flow and recover without duplicate publication. A local synthetic confirmation fixture tests the protocol; it does not establish that a real human-approved production flow exists.

## Delivery sequence and acceptance

1. Build a provider-neutral adapter and isolated synthetic issuer fixture. Test callback state/nonce/PKCE, signature/key rotation and issuer/audience/expiry failures; reject replay and unsafe return routes. Do not use OKF or external services.
2. Add session/proxy endpoints and browser adapter under an explicit flag. Test cookie attributes, CSRF/origin, request allowlist and header stripping, expiry/logout/cache purge, refresh races/failures and bounded stores. Native API authorization tests remain separate and authoritative.
3. Chrome: clean profile → login → accessible domain → conversation/proof; refresh, Back, expired session and reconnect to the same context, logout, wrong tenant/no domain, dark/light desktop/mobile and keyboard. A component test does not satisfy these gates.
4. Add the interactive confirmation adapter, then finish owner import/review/publication with conflict, lost-response and idempotent recovery scenarios. Audit receipt storage without recording private tokens/content.
5. Configure a real provider and trusted signer only when their identities/origins are supplied and the deployment scope is authorized. Keep production login and multi-instance readiness explicitly unqualified until verified.

## Consequences

This adds a session service and operational responsibility, but leaves knowledge storage, publication authority and native JWT verification intact. It avoids rewriting the business core to solve browser access. The immediate AUD-04 navigation correction can ship independently: URL-bound conversation selection and manual reauthentication do not imply that this session design is implemented.

No migration, real identity-provider provisioning, live approval or production session was performed. The complete local HTTP acceptance now connects a synthetic issuer and the real gateway CLI/Vite relay to the native API and existing synthetic PostgreSQL/Terminus data. It creates only personal synthetic conversations/episodes, exercises existing static rights and does not change publication/source/membership data. Earlier isolated tests used synthetic core transports. The console opt-in adapter is coded, but its React/browser journey has not been exercised; HTTPX cookie handling is not Chrome cookie-policy evidence. Focus revalidation hides the current workspace and preserves an unsent draft only if the verified session, identity and domains remain identical; changed/failed/expired identity clears it. The local relay avoids Vite’s generic proxy error logging of callback URLs and never records query/body content. This dev relay is not a production reverse proxy. Session credentials are discarded on shutdown. Until renewal exists, a new login is required at expiry. Late expired-session responses deliberately do not clear cookies, to avoid deleting a concurrently rotated session; explicit logout clears cookies, and the optional frontend now clears private caches on authentication failure. An uncertain logout is displayed as uncertain until a subsequent explicit attempt confirms absence. Routes for approval/publication, ingestion, ACL mutations and generic MCP are not exposed by the proxy. An independent confirmation adapter and reviewed workflow are required before expanding that surface.
